LangChain Deep Agents framework

Deep Agents is LangChain's higher-level agent harness for tasks that need more than a single model call and a few tools. It is built on LangChain and runs on LangGraph, so the agent can plan, use tools, write files, delegate work, stream events, pause for human input, and keep state across a longer run. The useful mental model for this workshop is simple: Deep Agents is the runtime around the model. The model still decides what to do next, but the framework gives it a workspace, a task list, subagents, skills, permissions, and a repeatable way to run.

For software engineers new to agent frameworks, the important part is where each behavior lives. Tools are Python functions. The system prompt is the coordinator's job description. The filesystem backend is where intermediate work and final artifacts are stored. Permissions define the allowed read and write boundaries. Skills are reusable instructions for a category of work. Subagents are smaller worker agents with their own prompts, tool lists, and optional permission rules. Once those pieces are visible, a long-running research agent becomes something you can inspect and change.

The framework is especially useful for research workflows because research is not one operation. A useful run has to break the task into steps, collect and normalize sources, keep notes outside the main context window, draft an artifact, check the draft against the sources, and leave enough evidence for a human to review. Deep Agents does not solve that by itself. It gives you the structure to express that process in code.

The construction point

The call to create_deep_agent is where the harness is assembled. In a small demo, it can take only a model, a few tools, and a prompt. In this workshop repo, the constructor is deliberately richer so participants can see how a practical agent is wired: model, tools, backend, permissions, skills, subagents, and coordinator prompt. 

from deepagents import create_deep_agent

agent = create_deep_agent(
    model=config.model,
    tools=[
        create_task_packet,
        record_source,
        classify_source,
        build_source_ledger,
        prepare_aiq_research_request,
    ],
    backend=_workspace_backend(config),
    permissions=_workspace_permissions(),
    skills=[str(config.skills_dir)],
    subagents=build_subagents(config),
    system_prompt=COORDINATOR_PROMPT,
)

Read this call as an interface contract. The agent can only call the tools you give it. It can only write where the backend and permissions allow it. It can only follow skills that are present in the skill directory. It can only delegate to the subagents you configure. That is the practical difference between "asking an LLM to research something" and building a research system that leaves useful artifacts behind.

The framework pieces

The table below is the vocabulary participants need before touching the code. Each row maps a framework concept to a concrete engineering decision in the repo.

Tools Typed Python functions for deterministic actions such as source records and ledgers. src/deep_research_agent/tools/research_sources.py

What the built-in runtime gives you

Deep Agents ships with capabilities that are easy to underestimate if you only look at the first tool call. The built-in planning tool lets the agent keep a visible task list. Filesystem tools let it read, write, edit, list, glob, and grep files instead of carrying every intermediate result in the message history. Context management lets large tool outputs and older state be moved out of the active prompt. Subagents let the coordinator send a focused job to another agent and receive a concise result. Skills let a team package a procedure, review rule, or integration pattern without rewriting the main prompt.

The point of the walkthrough is to make those capabilities legible. First, run the repo with mocked source data so the mechanics are clear. Then inspect how the workspace changes. Then add skills. Then add subagents. Then treat AI-Q or any other external capability as a skill-backed backend, not as a replacement for source discipline or review.

How to teach this section

Start with the constructor and stay close to the code. Ask participants to name what would break if each argument disappeared. Without tools, the agent has no reliable source records. Without a backend, the long run has no durable workspace. Without permissions, write behavior is too broad. Without skills, repeated process lives in one large prompt. Without subagents, source-heavy work crowds the coordinator's context. Without review artifacts, the result is hard to audit.

By the end of this first session, the group should be able to explain the Deep Agents framework from the outside in: a user message starts a run, the coordinator plans, tools perform narrow operations, files hold intermediate state, skills provide reusable procedures, subagents isolate focused work, and the final output points back to artifacts that can be reviewed.

1. Add one small tool

A Deep Agent still starts with ordinary tools. In this repo the tools are local helpers for source records, source ledgers, and AI-Q request contracts.

Tools should be small and inspectable. The agent can call them, but the tool itself should not depend on the model making a good judgment. Here, record_source does one narrow thing: it turns a title and URL into a normalized source record with a stable source ID. That stable ID can then travel through the ledger, the draft brief, and the review checklist. 

def record_source(title: str, url: str, source_type: str = "web") -> dict:
    return {
        "source_id": stable_id(title, url),
        "title": title,
        "url": url,
        "source_type": source_type,
        "retrieved_at": today(),
    }

Run the helper in the notebook and confirm it returns structured data, not prose.

This is the first important design habit: keep low-level operations narrow and typed, then let the agent compose them. If a source record is malformed, the bug should be in a short Python function, not hidden in a paragraph of generated text.

2. Create the Deep Agent

The main construction happens in create_agent(). The important idea is that Deep Agents gives the model a bigger runtime than simple tool calling: planning, filesystem tools, skills, subagents, and context management.

The call to create_deep_agent is the center of the walkthrough. It binds together the model, the deterministic tools, the filesystem backend, the permission rules, the skill directory, the subagents, and the coordinator prompt. Each argument is a design decision. Removing one should visibly change what the agent can do. 

from deepagents import create_deep_agent

agent = create_deep_agent(
    model=config.model,
    tools=[
        create_task_packet,
        record_source,
        classify_source,
        build_source_ledger,
        prepare_aiq_research_request,
    ],
    backend=_workspace_backend(config),
    permissions=_workspace_permissions(),
    skills=[str(config.skills_dir)],
    subagents=build_subagents(config),
    system_prompt=COORDINATOR_PROMPT,
)

In the repo, do not treat this as abstract. Point at each argument and say what it changes in the run.

For the group, the key distinction is between a simple agent and a deep agent. A simple agent can call tools. A deep agent can also manage files, split work across subagents, load procedural skills, and keep intermediate state out of the main context. That is what makes it suitable for longer research tasks.

3. Give the agent a workspace

Deep Agents expose filesystem tools such as reading, writing, editing, listing, globbing, and grepping files. This is the part that lets long tasks leave durable intermediate work instead of keeping everything in the conversation.

The workspace is what makes the run reviewable. A long research task will create notes, partial results, failed attempts, source records, and draft claims. If all of that lives only in the chat context, it is hard to inspect and easy to lose. The filesystem backend gives the agent a place to put those artifacts while keeping the project structure visible to the human reviewer. 

def _workspace_backend(config):
    from deepagents.backends import CompositeBackend, FilesystemBackend, StateBackend

    return CompositeBackend(
        default=StateBackend(),
        routes={
            "/workspace/": FilesystemBackend(
                root_dir=str(config.repo_root),
                virtual_mode=True,
            ),
        },
    )

Then restrict writes. The workshop agent should stage artifacts under the LLM Wiki paths and keep secrets out of reach.

Permissions are part of the lesson. The agent can read the workspace, but it should not be able to overwrite arbitrary project files or inspect secrets. In this repo, write access is limited to the wiki and raw artifact paths. That makes the expected output easy to find and the failure mode easy to spot. 

FilesystemPermission(
    operations=["read", "write"],
    paths=["/workspace/.env"],
    mode="deny",
)

FilesystemPermission(
    operations=["write"],
    paths=[
        "/workspace/llm-wiki/wiki/**",
        "/workspace/llm-wiki/raw/**",
    ],
    mode="allow",
)

4. Add skills

A skill is a procedure the agent can read. It is not a Python function. Use it when the important part is behavior, policy, or workflow.

Tools answer “what can the agent call?” Skills answer “how should the agent behave when it does this kind of work?” That makes skills a good place for source discipline, review rules, output templates, and backend-specific instructions. Skills are also easier for a team to review than a long prompt buried inside application code.

Skill What it teaches the agent
research-scout How to collect source-backed material without writing the final answer.
source-ledger How to preserve source IDs, caveats, and review questions.
wiki-curator How to stage durable draft files in the LLM Wiki.
aiq-research How to prepare an optional AI-Q request contract; live AI-Q requires NVIDIA's official skills and a running backend.

Read one skill and answer three questions:

This exercise should be concrete. Open a skill file, read its frontmatter, then read the instructions as if you were reviewing a teammate's pull request. A useful skill should say when it applies, what output it expects, and what behavior is out of bounds. If it cannot answer those questions, it is not ready to be part of the harness.

  • When should the agent use this?
  • What output shape does it require?
  • What should the agent refuse or mark for review?

5. Add subagents

Subagents are useful when a task needs a narrower context or a different permission boundary. In Deep Agents, configured subagents are exposed through the task delegation path.

Subagents are not there to make the system look elaborate. They are useful when separation improves the work. A source scout can focus on source records. A synthesis writer can focus on turning records into a draft. A reviewer can inspect staged files without permission to edit them. The coordinator keeps the overall task moving instead of carrying every detail in one context.

Subagent Job Tools
source-scout Collect and classify sources. record_source, classify_source
synthesis-writer Draft the brief from source-backed notes. create_task_packet, build_source_ledger
skill-router Prepare optional backend requests. prepare_aiq_research_request
skeptic-reviewer Read staged files and flag problems. Read-only filesystem

Find _reviewer_permissions() and explain why that subagent cannot write.

This is the most important subagent boundary in the repo. A reviewer that can rewrite the draft is not just reviewing; it is changing the artifact it is supposed to inspect. Keeping it read-only makes the review output easier to trust.

6. Run the agent

First run the deterministic notebook path. Then run the live agent only if model credentials are configured.

The notebook path is the teaching path. It lets participants inspect the contracts without depending on model credentials, live retrieval, or AI-Q. Once the table understands the files, they can run the live agent and compare what changed. That comparison is the lesson: the same harness shape should remain visible whether the backend is mocked, local, or live. 

uv run --group notebook jupyter lab notebooks/deep_research_agent_walkthrough.ipynb
uv run deep-research-agent \
  "Compare three current approaches to long-running AI research agents.
   Use public sources only.

   Stage a brief, source ledger, open questions, and run log."

Expected files:

The final answer from the model is not the main deliverable. The main deliverable is the set of staged files. If those files are missing, unclear, or uncited, the run did not produce a useful research artifact. 

llm-wiki/wiki/research-briefs/<topic>.md

llm-wiki/raw/<topic>_run_log.md

7. Review the run

The review is the point of the exercise. Do not score the run by whether the prose sounds good.

Review the harness by asking whether another engineer could resume the work. They should be able to see what the task was, which sources were used, what the agent wrote, what it could not verify, whether AI-Q was used, and what should happen next. If the run hides those details, the harness needs another pass.

  • Does every central claim have a source ID?
  • Are source notes separate from synthesis?
  • Did the run log record AI-Q as live, unavailable, or skipped?
  • Did any subagent exceed its job?
  • Did the reviewer catch at least one weak or unsupported claim?
  • What should be changed in the harness before the next run?

Pass condition: the team can explain the Deep Agents construction from tool to skill to subagent to staged file.

A strong table can also name the next improvement. Examples: add a stricter source-ledger test, install the official AI-Q skills, add a corpus retrieval skill, make the run log more structured, or add an approval gate before promoting a draft.
